## Current State (measured against `forge/a-rung-is-never-skipped` @ 5243b8f — this session's actual checked-out HEAD; the earlier "current branch: main" snapshot was stale)

**Two separate witness mechanisms exist, not one:**

(A) The POSITION LADDER (`<!-- position ... -->` block in a product's markdown, `impl_position.py` + `cmd_position`/`cmd_gate`/`cmd_step` in `implementation_cli.py`). Items are `record`/`notebook`/`rehearsal`/`shard` witnesses, each either two-state (bool) or `:level`-marked (rung-valued). `derive()` recomputes every mark FRESH from live evidence on every read — `position_state` never trusts an on-disk tick. `_skipped_rung_detail` (already merged on this branch) refuses `POSITION_RUNG_SKIPPED` when a forward `--target-level` move's predecessor rung isn't attained, and explicitly EXEMPTS two-state items from that specific check, with a stated reason: they're identical at every rung, so folding them into rung-skip would be "whole-sequence completeness wearing this rule's name." Their own docstring points at the real enforcement for two-state items: `impl_availability.launch_available`'s `SEQUENCE_NOT_REACHED`.

(B) ORDINARY AGREEMENTS (`agreements_state` in `implementation_cli.py`, checklist items under other `## ` headings in AGREED.md, unrelated to the position block). Witnessed by an inline `` `test_<id>` `` token, graded ONLY by `test_function_names()` — an `ast.walk` over `tests/*.py` that checks whether a function BY THAT NAME EXISTS. `disagrees` fires only when the named test function is DEFINITELY ABSENT from a fully-parsed `tests/`; a test that exists and fails reads `unmeasured`, which never gates. This is the mechanism the brief's docstring quote describes, and it is real, unaddressed, and distinct from (A).

**The brief's framing needs correction on one major point.** For (A), the target (`implementations/Domain_Adaptation`, product `MIL-CREDA`) has ALREADY solved the "a run is not a verdict" problem for its rung-1 item, and it works, verified by reading the actual files:

- `MIL-CREDA/AGREED.md` position block, item 1: `- [x] 1. ... the suite is green ... Two-state on purpose ... `@notebook Notebooks/verification.ipynb``
- `MIL-CREDA/Notebooks/verification.ipynb` runs `pytest.main(["-q", str(ROOT / "tests"), "--rootdir", str(ROOT)])` and then `assert code == 0, f"test suite failed (pytest exit code {code})"` — a failing suite makes the assert RAISE, which lands in the notebook's own cell `outputs` as an error, which `notebook_execution()` reads as `status: "errored"`, which makes `_derive_notebook` return `False` (not "executed"), which position derives as unsatisfied, which `position_state` reports as a disagreement if ticked, which `launch_available`/`position_honest` refuses `POSITION_DISAGREES`/`SEQUENCE_NOT_REACHED` on the very next `gate`/`step` call — with NO explicit "position refresh" step required, because everything is recomputed fresh on every gating call.
- The notebook's final cell prints `SOURCES-SHA256 <hash>` via `report_digest.stamp()` — the existing `DIGEST_MARKER`/`sourcesMatch` currency mechanism, already wired.

So `impl_steps.py`'s RUNNER (`raised`/`returned`) is not the ONLY place a real pass/fail verdict already reaches evidence — it is ALSO already reachable through `@notebook` + an assert the notebook author chose to write. This is real for THIS target today, but it is an accident of notebook authorship, not a forge-level guarantee: nothing in `notebook_execution`/`_derive_notebook` knows or enforces that an "executed" cell actually checked a suite's exit code. A verification notebook without the `assert` would silently launder a red suite as `executed`, and the forge would have no way to tell the difference. This is the actual, general form of the gap: **the forge has no witness kind whose derivation is intrinsically tied to a callable's raise/return outcome** — everything that currently reaches that outcome does so by convention (a notebook author remembering to assert), never by structure.

**`impl_steps.run_step`** (`.claude/skills/_core/implementation/impl_steps.py`) is the structural primitive that closes this by construction: it resolves a target-declared `{module, function}` callable under the target's own interpreter, in a subprocess, and writes exactly one of five states to a verdict file — most importantly `"returned"` (no exception) vs `"raised"` (exception, with `error` text) vs `"unresolvable"` (module/function/callable missing). `cmd_step` (already exists) calls this and appends a `kind: "step"` ledger event (`.implementation/position.jsonl`) carrying `outcome`, `exitStatus`, `error`, `session`, `at` — but explicitly, by documented design, NO digest field ("no digest field: `notebooks_state` already recomputes `source_digest` fresh against a notebook's own `DIGEST_MARKER` output, so a ledger-carried copy would be redundant"). That reasoning is scoped to steps that produce their own self-stamped artifact (a notebook); it does NOT hold for a step whose entire purpose IS the witness (e.g. a bare `unittest`/`pytest` runner callable with no artifact of its own) — there, the ledger event is the ONLY record, so it MUST carry the digest, or currency cannot be checked at all.

## Design Fork — resolved

**Recommendation: a fourth option, not exactly any of the three offered — reuse the existing two-state ordinary-sequence-item pattern (already proven by item 1's `@notebook` usage), wired to a NEW witness kind that reads a step's ledger outcome directly, instead of routing through a notebook.**

Reasoning that killed the alternatives, checked against the actual code:

1. **Option 1 (leveled encoding) — rejected.** A red/green verdict has no natural rung; forcing one would be exactly the "inventing one on the repository's behalf" `_record_scale_level`'s own docstring refuses to do for `@record`. Dishonest by the code's own stated standard.

2. **Option 2 (fold two-state items into the rung-skip check) — rejected, and unnecessary.** It directly reverses `5243b8f`'s own reasoned decision, and the reasoning is sound: a two-state item is identical at every rung, so refusing a rung climb over it is "whole-sequence completeness wearing this rule's name" — the exact "guard that can never legitimately fire, or fires for the wrong reason" defect class this codebase keeps closing. It is also unnecessary: **the ordering guard two-state items already get — `SEQUENCE_NOT_REACHED` via `launch_available`, checked fresh at every `gate`/`step` call, independent of the rung-skip check entirely** — already blocks any later item (including a job launch) while an earlier two-state item's on-disk mark disagrees with a fresh re-derivation (`POSITION_DISAGREES`, checked by `position_honest` BEFORE `SEQUENCE_NOT_REACHED` even runs). Item 1 in the real target proves this live today.

3. **Option 3 (precondition orthogonal to the ladder, like `_require_no_open_defect`) — the right SHAPE for a truly new precondition, but not needed here**, because the two-state-item + sequence-ordering combination already IS "a property of the tree, checked before anything downstream," without inventing a second gating layer. Introducing a parallel precondition mechanism when the ladder already has one that fits would duplicate the check and create two places that could disagree about what "the suite is green" means.

**The actual gap to close is narrower than the fork implies**: not "how do two-state items interact with the ladder" (already correct), but "give the forge a witness kind whose derivation is a structural raise/return outcome instead of a notebook-authorship convention, and give it currency." Concretely:

- Add `"step"` to `WITNESS_KINDS` (mirrors `__steps__`'s own vocabulary — `@step <stepName>` where `stepName` is one of the target's own `__steps__` keys, exactly like `@rehearsal <jobName>` already names a job).
- `_derive_step`/`_derive_step_level` fold the ledger's `kind: "step"` events for that step name, latest-wins: `outcome == "returned"` and current digest → `True`/top rung; `outcome == "raised"` → `False`/floor rung (a leveled step witness is legitimate here, unlike the suite-as-a-whole, IF the target genuinely has rungs of "how much of the suite ran" — but for a bare test-runner callable, two-state is the honest default, exactly matching item 1's own stated reasoning: "Two-state on purpose — it runs here and nowhere else, and giving it a rung would be the position asserting a state it does not have.")
- `outcome == "unknown"` (RUNNER died mid-call) or no event at all → unmeasured (`None`), never `False` — matches the existing `derive()` doctrine throughout.

## Where the verdict lives, what the digest covers, how it expires

**Storage**: the existing `.implementation/position.jsonl` ledger, as a NEW field on the `kind: "step"` event (or a new `kind` if reusing `cmd_step`'s existing event shape is judged to conflict with its own "no digest field" doctrine for other steps — that reasoning was scoped to self-stamping steps and does not transfer). Read fresh via `impl_position.read_events` on every gating call, exactly like every other evidence source — no caching layer to go stale.

**Digest scope — this is the one place the brief's suggested precedent ("the way `sourcesMatch` already works for notebooks") is actively wrong if copied verbatim.** `source_digest(target, package)` hashes every `.py` under `src/` and DELIBERATELY EXCLUDES `tests/` — verified by reading its own docstring, which records this as a past incident: including `tests/` once made "adding any test at all mark every report stale," forcing an unwanted full-campaign re-stamp. That exclusion is correct for a NOTEBOOK's report, whose claims are about `src/` and never import `tests/`. **It is wrong for a suite witness, whose entire claim is about `tests/`.** A suite-verdict digest that reused `source_digest` unchanged would let someone add, remove, or gut a test file without ever invalidating a green verdict — the exact staleness bug this codebase already fixed once, reintroduced by copying the wrong precedent. The digest for this witness kind must cover `src/` **and** `tests/`, walked the same way `test_function_names`/`unparsable_tests` already walk `tests_dir.rglob(...)` — reusing that exact scope, not `source_digest`'s.

**Expiry**: automatic and structural, not time-based — the digest recorded at the moment the step ran is compared against a freshly-computed one on every read; any change to `src/` or `tests/` between the run and the read makes it unmeasured (never a stale `True`), exactly the `recordCurrent`/`sourcesMatch` doctrine `_derive_record`/`_derive_notebook` already state.

## Whether the agreements composition is sound — measured, not assumed

**Sound today, for this target, verified by direct comparison — not structurally guaranteed by the forge.** `agreements_state`'s `test_function_names(target / "tests")` walks the ENTIRE `tests/` directory (`tests_dir.rglob("test_*.py")`, every `FunctionDef`/`AsyncFunctionDef` name, no filtering). `verification.ipynb`'s suite cell runs `pytest.main(["-q", str(ROOT / "tests"), "--rootdir", str(ROOT)])` — the identical directory, unrestricted (no `-k`, no marker filter, no path narrowing). So today, a green run of that notebook genuinely means every `test_<id>` the ast walk could find was exercised and passed — the composition "green suite + `test_<id>` present" really does mean "that test passed," verified by reading both scopes side by side, not assumed from naming similarity.

**But nothing pins this.** No code enforces that whatever callable a `@step`/`@notebook` suite witness names actually runs the WHOLE of `tests/` with no narrowing. A future edit narrowing the pytest invocation (a `-k` filter, a subdirectory, a `--ignore`) would silently break the composition: the ast walk would still find `test_<id>`, the suite witness would still read green, and a test that was quietly excluded from the run would read as passing when it was never executed. If the composition rule ("green suite backs every declared agreement witness") is adopted as a shortcut for closing gap (B), it needs its own guard — either the forge demands the suite-running declaration name an unrestricted `tests/` invocation (structurally, the same way it demands `__steps__`/`__levels__` exist at all), or the composition is left as advisory documentation a target chooses to honor, not something the forge verifies. Recommend NOT wiring (B) to (A) automatically in this change; treat them as two separate, sequenced pieces of work.

## Cross-repository split

**Forge work** (this repo, `.claude/skills/_core/implementation/` + `.claude/skills/proposal-implementation/scripts/implementation_cli.py`): add the `step` witness kind and its derivers to `impl_position.py`; extend `cmd_step`'s ledger event (or add a sibling command) to carry the tests+src digest; classify the new refusal(s) in `GATING_REFUSALS` with a proper `WORK_STATE`/question-or-command resolution, matching the settled four-exit table:

- target declares no such `__steps__` entry → `STEPS_UNDECLARED` already exists and is already published as a `question` ("declare them now, or record why the work runs outside this command, and why?") — reuse verbatim, no new code needed for this exit.
- verdict stale (digest moved) → publish as a `command` (re-run `step`), mirroring `POSITION_STALE`'s existing `_refusal_command` pattern.
- verdict red (`outcome == "raised"`) → publish as a `command` (re-run `step` after a fix), **never a question** — matches the settled requirement exactly and matches how `POSITION_DISAGREES` already resolves (`_resolve_position_disagrees`, a command, never a question) for the identical reason: a discussion cannot fix code.
- red because the AGREEMENT aged, not the code → this is `settle --reverse`'s existing territory (agreements half, mechanism (B)), untouched by (A)'s new witness kind — no new plumbing needed there, it already requires a written `## Reversed` paragraph and never lifts a code-level block.

**Target work** (`implementations/Domain_Adaptation`): declare a suite-running `__steps__` entry (module+function, e.g. a bare `pytest.main`/`unittest` wrapper with no notebook), and either migrate item 1's witness from `@notebook Notebooks/verification.ipynb` to `@step <name>` or add a new item — a target-owned decision, not the forge's to make. These are separate repos, separate suites, separate commits, per this project's own maintenance rule; nothing in this exploration blends them.

**What the forge does about a target that has NOT declared the callable**: refuses, never silently passes. `STEPS_UNDECLARED` (already exists, already a published `question`: "this target declares no `__steps__` at all... declare them now, or record why the work runs outside this command, and why?") is the exact existing exit for "the target must grow the check" — this is not a gap to fill, it's already correct and already matches the settled requirement's first row verbatim. The one thing to add is a parallel-but-distinct message when `__steps__` exists but carries no entry usable as a `@step` witness's operand (i.e., the position item names a step the target's own dict doesn't have) — mirrors `STEP_UNKNOWN`'s existing pattern (`INVOCATION_DEFECT`, "the detail lists the real ones").

## Risks

- **Roster-scraper blind spot, confirmed by reading `raised_refusal_codes`**: it does `ast.walk` starting at the `cmd_<command>` `FunctionDef` node found in the module, descending into NESTED closures but never into a call to a separate top-level helper function. `FORGE_DEFECT_OPEN` (raised only inside the top-level `_require_no_open_defect`, called from `cmd_step` et al.) is provably invisible to it — and, checked directly, is genuinely absent from `GATING_REFUSALS` too, so no test asserts either side and it silently carries no published `resolve`. **Implication for this change**: if the new suite-witness refusal is implemented as a raise inside a NEW top-level helper (mirroring `_require_no_open_defect`), it will (a) never be counted by `test_the_derivation_finds_the_measured_sixty_five`, and (b) if manually added to `GATING_REFUSALS` anyway, will actively FAIL `test_every_gating_refusal_is_classified`'s `roster - raised == []` assertion, because the scraper will never find it raised. The safe shape is `_skipped_rung_detail`'s own pattern: a helper that RETURNS a detail string (or `None`), with the actual `raise Refused(...)` staying textually inside `cmd_position`'s (or whichever `cmd_*`'s) own body, so the scraper counts it and the roster machinery forces a real resolution — not raised from inside a separate helper function.
- The (B) agreements half (per-agreement `test_<id>`, never executes) remains open after this change unless explicitly scoped in; conflating it with (A) risks the unsound-composition trap above.
- `require_clean_worktree`/`_require_no_open_defect` already run before `cmd_step`; a suite-running step still needs `INTERPRETER_ABSENT` handling exactly as `cmd_step` already provides — no new work there.
- Vocabulary floor: `"step"` as a witness kind name and `"src"`/`"tests"` as digest-scope words are all already forge vocabulary in use; no target-specific word risk detected in the design as scoped. Not independently re-run (per the brief's own instruction to run suites rather than reason about it) — flagged for `sdd-apply`/`sdd-verify` to actually run `FORGE_VOCABULARY_FLOOR`.

## Ready for Proposal

Yes. The design fork has a clear, code-grounded answer (extend the existing two-state-item + `SEQUENCE_NOT_REACHED` pattern with a new `step` witness kind, not a ladder-rule change and not a parallel precondition mechanism), the digest scope question has a concrete, evidence-based answer that corrects a naive copy of the notebook precedent, and the cross-repo split is already mostly paved by existing, correctly-behaving refusal codes (`STEPS_UNDECLARED`, `STEP_UNKNOWN`). Recommend `sdd-propose` scope this to mechanism (A) only (the `step` witness kind + digest), explicitly deferring mechanism (B) (agreements `test_<id>` execution) as a separate, later change — conflating them was not asked for and the composition-soundness finding above shows why that would be premature.
